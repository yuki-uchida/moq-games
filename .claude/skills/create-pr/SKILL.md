# PRの作成とマージ

ユーザーの明示的な指示と実行環境の制約を優先する。

## 開始時

- 質問のみの依頼には公開作業を行わない。push・PR・マージを行わないという明示指示があれば、その境界で止める。
- `git status --short` で既存の変更を記録し、今回の対象と分ける。
- `git ls-remote --symref origin HEAD` と `gh auth status` を別々に実行する。前者はGitの読み取り接続だけを確認し、push権限の証明にはしない。gh未認証でも、検証・コミット・許可された作業ブランチへのpushを独立して進める。

1. `git status`、現在のブランチ、リモートとPRのベースを確認し、無関係な変更を除外する。公開済み履歴の書き換えやforce-pushは明示的な許可なしに行わない。コンフリクトは解消し、変更を再検証する。
2. 対象の差分を確認し、リポジトリが定めるチェックを実行してからコミット・pushする。失敗・未実行のチェックを成功扱いしない。
3. 正しいリポジトリとベースにPRを作成する。タイトルは日本語で書く。概要はリポジトリの記載規則に従い、現在の差分に合うよう簡潔に書く。
4. PRのHEADとコンフリクトを確認し、コンフリクトがあれば解消する。マージ前のCIやレビューは待たず、保護ルールは回避しない。
5. 都度ユーザーに確認せずスカッシュマージし、マージ完了を確認する。失敗や未完了は報告し、成功と偽らない。

PRを作らない・マージしないとの指示がある場合はその時点で止める。認証、権限、保護ルール、利用できないチェックなどで進めない場合は状況と残作業を報告する。

## 終了前

1. 対象ファイルの検証結果とコミットSHAを記録する。未実行や失敗を成功扱いしない。
2. リモートHEAD、PRのHEAD・マージ状態を確認し、無関係な既存変更は開始時の記録と照合する。
3. 認証・権限・保護ルール・必須ツール不足は再試行ループにせず、可能な独立工程を済ませて未完了として報告する。
4. 最終応答には検証結果、commit/push/PR/mergeの到達点、ブロッカーと残工程を簡潔に記載する。明示的な作業範囲の制限がある場合は、その制限も記載する。

pushやマージをhookから実行しない。コマンド許可rulesを公開作業の完了判定に流用しない。

スクリプト変更時は `node --test .claude/skills/create-pr/scripts/check-completion.test.mjs` を実行する。
